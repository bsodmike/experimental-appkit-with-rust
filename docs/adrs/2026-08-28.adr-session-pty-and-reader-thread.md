# ADR: the session, the pty, and the reader thread

- Date: 2026-08-28
- Status: Accepted
- Scope: `terminal-core` `session`; the new `terminal-pty` crate; workspace root

## Context

PRD §7 and §9 describe the running terminal: a mutex behind an opaque handle, a
dedicated reader thread that parses, a coalesced wake-up, replies written back
upstream, and a shutdown that leaves nothing running. This slice builds all of
that, and it needed a second crate to do it.

## Decisions

### `terminal-pty` is a separate crate, and the workspace is now real

The PTY and the shell process are Rust's (PRD §5), but they are platform code.
Putting them in `terminal-core` would give the engine a dependency and a POSIX
floor, against the crate's one rule: *if the engine ever needs a Mac — or any
particular OS — in order to be tested, something has leaked*. So the repository
gains a workspace root and `terminal-pty` alongside the engine. `terminal-ffi`
joins them later (PRD §14, §19).

`terminal-pty` depends on `terminal-core`, not the other way round: the platform
half knows about the engine, and the engine knows nothing.

Dependencies: `pty-process` for opening the pty and spawning the child as a
session leader with a controlling terminal, `rustix` for `poll`, the self-pipe
and signals. Both are thin over the syscalls; neither pulls in a runtime.

### The lock is in the engine, and the wake-up fires outside it

`Session` owns `Mutex<Emulator>` — screen plus parser, because the parser is
stateful across reads and must stay in step with the screen it drives. The
wake-up callback is given at construction rather than registered later, so
there is no second lock to take and no window in which a callback is half
installed.

The callback is called *after* the lock is released. A callback that re-entered
the terminal API while the lock was held would deadlock on a non-reentrant
mutex; that is not a hypothetical, since it is exactly what a `drawRect:`
triggered synchronously would do.

`render_into` clears the dirty flag *before* copying, so a write landing
mid-copy leaves the flag set and costs one redundant redraw. Clearing it
afterwards would silently swallow that write until something else happened to
set the flag again.

A poisoned lock is recovered rather than propagated (`into_inner`). A panic must
never cross the FFI boundary (PRD §12), and a terminal drawing one damaged row
beats a terminal that stops drawing.

### The reader thread parses, and answers

`Terminal::spawn` starts a named `pty-reader` thread that blocks on the pty,
feeds what it reads into the engine, and writes any reply straight back down its
own handle to the descriptor. The UI thread never parses: parsing is unbounded
work driven by whatever the program decides to print.

The pty is split into two handles over the same open file description — one for
the reader, one for the writer — so a blocking read never holds anything a write
needs. A single handle behind a mutex would have the reader holding the lock
while parked in `poll`, which is to say permanently.

### Stopping is ordered, and `Drop` does it too

Shutdown is: silence the wake-up, fire the interrupt, join the reader, then hang
up the child and reap it. The interrupt is a self-pipe polled alongside the pty,
because a thread blocked in `read()` cannot be asked to stop by a flag it never
looks at, and closing the descriptor under it races with descriptor reuse.

The child gets `SIGHUP` first — that is what a terminal closing means, and a
shell hangs up its own children in turn — then `SIGKILL` after a 500 ms grace.
A child that traps `SIGHUP` must not be able to keep the pty, and therefore the
reader thread, alive.

`Drop` runs the same sequence, so a caller who forgets still cannot leave a
thread writing into memory that is going away.

### Resize goes to the engine first, then the kernel

`Terminal::resize` reflows the engine and then sets the window size, which is
what makes the kernel deliver `SIGWINCH`. The other order has a race: a program
that redraws immediately on `SIGWINCH` would have its output land in a screen
still laid out for the old width.

### The hangup is reported through the same wake-up

When the reader thread stops, it sets a flag and marks the screen dirty, so the
UI redraws once more and can notice the shell has gone. That keeps one
notification path rather than inventing a second callback for the exit.

## Consequences and deferrals

- `Session::feed` and `Screen::advance` both return the owed bytes; the reader
  thread is the caller that actually writes them.
- The §16.5 reflow maintenance thread does not exist yet. When it does, it joins
  the same shutdown sequence, which PRD §7 already anticipates ("**both**
  threads").
- Nothing decodes keystrokes yet: `Terminal::send` takes bytes, and the
  key-encoding slice (PRD §8) is what will produce them.
- The reader thread's error handling is coarse: any read or write error other
  than `EINTR` ends the loop and is reported as a hangup. A terminal whose pty
  has failed has nothing left to show.
